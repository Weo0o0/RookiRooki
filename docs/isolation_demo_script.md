### ⚠ 꼭 지킬 규칙 3가지

1. **승인은 장면 1의 스크립트가 「실습 트래픽 생성 끝.」을 출력한 뒤에만 합니다.** `lab-traffic.sh`는 4번째 줄에 `set -eu`가 있어서, 도중에 attacker를 끊으면 다음 명령이 실패하는 순간 스크립트가 멈춥니다(hydra와 C2 부분만 `|| true`로 실패를 넘김). 그러면 뒤 단계 경보가 만들어지지 않습니다.
2. **누를 링크는 SQLi 진짜 공격 하나입니다.** 장면 1~3이 끝나면 `.100`의 SEV1 링크가 4개(SQLi, XSS, SSRF 성공, 장면 3 오탐) 옵니다(1-1절 표). Discord 메시지와 확인 페이지에는 **요청 주소가 나오지 않아서**, SQLi 진짜 공격과 장면 3 오탐은 둘 다 `SQLI (1000001)`로 똑같이 보입니다. 고르는 법:
   - 진짜 공격은 장면 1에서 먼저 났으니 **SQLI 메시지 중 먼저 온 것**(번호가 작은 것)입니다.
   - 확인 페이지의 **번호**를 대시보드 경보 상세에서 찾아 요청 주소에 `admin'`·`OR`이 있는지 보고 승인합니다.
   - XSS 링크: 누르지 않음 — `/search`가 항상 200이라 SEV1이어도 실행 증거가 아님(`rules/isolation_criteria.md` 2절)
   - 장면 3 오탐 링크: 누르지 않음 — 「링크가 와도 사람이 내용을 보고 거른다」는 설명에 활용
3. **토큰은 10분 동안만, 한 번만 쓸 수 있습니다**(`backend/isolation.py:15`). 장면 1이 끝나면 장면 5까지 10분 안에 진행합니다. 시간이 지나면 확인 페이지에 `Token expired`가 나옵니다. 그때는 장면 1을 다시 돌려 새 경보·새 링크를 받습니다.

### 장면 3 명령 — 실습망 안 attacker → victim-web 평범한 검색 한 건

(attacker_터미널.4) — `.venv` 불필요
```bash
docker exec attacker curl -sS -o /dev/null -w "search HTTP %{http_code}\n" "http://172.28.0.10/search?q=european+union+select+committee"
```
- 기대 출력: `search HTTP 200`
- 실제 녹화에서 같은 검색어가 SID 1000001, HTTP 200, SEV1 경보 2건을 만들었습니다(`.50`, `DEMO_REAL_ALERTS` id 167·170).
- 출발지가 `.100`인 같은 요청도 경보가 나는 것을 **오프라인으로** 확인했습니다(실습망 IP pcap + Suricata + `rules/custom.rules`, 2026-11-26). **실시간 캡처에서는 리허설 1회차에 확인**합니다.
- SQLi 룰에는 횟수 조건이 없어서 한 번만 보내도 경보 1건이 납니다(`custom.rules:3`).

### 장면 6·8 확인 명령

(attacker_터미널.4) — `.venv` 불필요
```bash
# 장면 6) 격리 후: 둘 다 실패해야 함 (실패 문구는 환경에 따라 다름)
docker exec attacker ping -c 2 -W 2 172.28.0.10
docker exec attacker curl -sS --connect-timeout 3 http://172.28.0.10/health
```

| 2 | Discord 메시지가 안 옴 | 자동 알림이 켜져 있는지(새 탭이면 다시 설정), 테스트 발송이 되는지, SEV1 경보가 실제로 있는지 | 웹 토스트·알림 이력으로 설명하고 진행 |
| 3 | 오탐 경보가 안 뜸 | 출력이 `search HTTP 200`인지, Suricata 창이 켜져 있는지 | 실제 녹화의 `.50` 사례(Mock `?mock=real`)로 설명 |
| 4 | 저장 실패 | 담당자가 50자를 넘는지, 백엔드 창 오류 | 판정·메모만 저장하고 진행 |

| 5 | 「Isolation is disabled」 | 서버 스위치 `ISOLATION_ENABLED=1` | 서버 재시작 후 장면 1부터 |
| 5 | 「Token expired」 / 「Token already used」 / 「Invalid token」 | 10분 지남 / 이미 쓴 링크 / 서버를 재시작해 토큰이 사라짐 | 장면 1 다시 실행해 새 링크 |
| 5 | 「Docker permission denied」 | 서버를 켠 계정이 `docker` 그룹인지(`id -nG`) | **5절 대체 시연(A단계)** 으로 전환 |
| 5 | 「Target not allowed」 | 누른 링크의 출발지가 `.100`인지 | 올바른 링크로 다시 |
| 6 | 승인했는데 ping 성공 | 승인 결과 문구, 백엔드 창 오류 | 대체 시연으로 전환, 끝난 뒤 원인 기록 |
| 7 | 확인 페이지를 닫아서 「격리 해제」 버튼이 없음 | — | 아래 「해제 명령」 |
| 7·8 | 해제가 안 되거나 IP가 바뀜 | 백엔드 창 오류 | 5절의 응급 복구 |

**해제 명령** (확인 페이지를 닫았을 때. Ubuntu 창 아무거나, `.venv` 불필요. 실습망이 아니라 내 컴퓨터의 백엔드로 보내는 요청)
```bash
curl -sS -X POST http://127.0.0.1:8000/api/unisolate -H "Content-Type: application/json" -d '{"ip":"172.28.0.100"}'
curl -sS http://127.0.0.1:8000/api/isolation/status
```
첫 줄 응답의 `status`가 `unisolated`(또는 이미 붙어 있으면 `already_connected`), 둘째 줄의 `isolated_ips`가 `[]`이면 해제된 것입니다.

## 5. 대체 시연 (A단계: 명령 안내만)

**언제 쓰나:** 리허설이 3번 연속 통과하지 못했거나, 발표 직전·도중에 격리가 불안정할 때. **격리 장면(5~8)만 빼고** 아래로 바꿉니다. 트리아지(장면 3·4·9)는 격리와 상관없이 그대로 합니다.

| 순서 | 할 일 | 말할 문장(예) |
|---|---|---|
| 1 | 장면 1~4를 그대로 진행 | — |
| 2 | 경보 상세의 **대응 안내(플레이북)와 복사 버튼**을 보여 줌 (지금 있는 기능) | 「자동으로 끊지는 않고, 분석가가 따라 할 안내를 줍니다.」 |
| 3 | 리허설 **성공 회차 녹화**를 보여 줌 (있다면) | 「리허설에서 실제 격리가 동작한 화면입니다.」 |
| 4 | 설계를 말로 설명: 사람 승인 + 1회용 토큰 + 허용 IP 1개(.100) + 해제 가능 | 「안정성을 위해 발표에서는 안내 방식으로 보여 드립니다.」 |
| 5 | 장면 9 (조치 상태를 「안내만」으로 저장) | 「안내만 한 경우도 기록으로 남깁니다.」 |

**응급 복구** (격리된 채 해제가 안 될 때, 최후 수단. 컨테이너를 새로 만들어 compose에 고정된 `172.28.0.100`으로 다시 붙입니다. 백엔드의 격리 기록과 어긋날 수 있으니 끝난 뒤 백엔드를 다시 켜는 것을 권장)

(attacker_터미널.4) — `.venv` 불필요
```bash
cd ~/RookiRooki/scenarios/lab
docker compose up -d --force-recreate attacker
docker exec attacker ping -c 2 -W 2 172.28.0.10
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' attacker
```

## 7. 예상 질문

| 질문 | 답 |
|---|---|
| 왜 자동으로 안 끊고 사람이 승인하나요? | 오탐으로 정상 사용자를 끊을 수 있기 때문입니다. 장면 3처럼 평범한 검색어도 SEV1이 됩니다. |
