## 1. SID / 심각도 표 (사실)

| SID | 종류 | 기본 SEV | 올라가는 조건 | 룰이 잡는 조건 | 근거 |
|---|---|---|---|---|---|
| 1000001 | sqli | SEV3 | HTTP 200이면 SEV1 | 요청 주소(URI)에 따옴표 뒤 `or`/`and`/`\|\|`, 따옴표 뒤 `--`/`#`/`/*`, `union (all) select` | `custom.rules:3` (rev 2) |
| 1000002 | xss | SEV3 | HTTP 200이면 SEV1 | `<script` `<iframe` `<svg` `<img` `<body` `<object` `<embed`, 이벤트 속성 `on…=`, `javascript:` | `custom.rules:5` (rev 1) |
| 1000003 | bruteforce | SEV2 | 없음 | victim-pc `172.28.0.11:22`로 같은 출발지가 60초 안 새 연결(SYN) 4회 이상 | `custom.rules:7` (rev 2) |
| 1000004 | portscan | SEV3 | 없음 | 22·80이 **아닌** 포트로 같은 출발지가 10초 안 SYN 20회 이상 | `custom.rules:9` (rev 2) |
| 1000005 | c2_beacon | SEV2 | 없음 | 포트 8443으로 같은 출발지가 30초 안 SYN 5회 이상 | `custom.rules:11` (rev 1) |
| 1000006 | ssrf | SEV3 | HTTP 200이면 SEV1 (403은 SEV3 유지) | `/fetch?`로 시작하는 요청의 `url=`이 `http`/`https`/`file`/`gopher` + 내부 주소(`172.28.` `127.` `localhost` `10.` `192.168.` `169.254.`), 주소 앞 `x@` 형태 포함 | `custom.rules:13` (rev 1) |

- 카테고리·기본 SEV: `backend/eve_parser.py:5-10`
- 격상 규칙: `backend/eve_parser.py:101` — `sqli`·`xss`·`ssrf`이고 같은 요청의 HTTP 응답이 200일 때만 SEV1. 나머지는 기본 SEV 그대로.

> **용어** · SYN: TCP 연결을 처음 열 때 보내는 패킷. 「새 연결 시도 1번」으로 보면 됩니다. · 격상: 기본 심각도를 더 높은 단계로 올리는 것.

**셀프 확인 명령** (Ubuntu 창 아무거나, `.venv` 불필요)

```bash
cd ~/RookiRooki
# 작업 문서에 적힌 명령 (rg가 설치돼 있을 때)
rg -n "1000001|1000006|SEV1|SEV3" backend/eve_parser.py | head -20
# rg가 없으면 아래 세 줄로 같은 확인
sed -n '4,11p' backend/eve_parser.py          # CATEGORIES 6줄이 위 표와 같아야 함
grep -n 'severity = "SEV1"' backend/eve_parser.py   # 101번째 줄이 나와야 함
grep -n "sid:" rules/custom.rules | cut -c1-120     # 3,5,7,9,11,13번째 줄에 SID 6개
```

## 2. 룰별 「격리 권장 여부」 (제안)

| SID | 종류 | 격리 권장 (제안) | 이유 | 카탈로그에 적힌 오탐 가능 사례 (`rule_catalog.json`의 `false_positives`) |
|---|---|---|---|---|
| 1000001 | sqli | SEV1이면 **권장**, SEV3이면 **안내만** | 응답 200이면 공격이 통했을 가능성이 있음. 단 SEV1이어도 정상 검색어 오탐이 실제로 있었으므로(`triage_templates.md` 1절) **요청 주소를 보고** 승인 | ① 따옴표 뒤 `--`가 오는 일반 문장(11-24 재현) ② 검색어에 `union select`가 그대로 든 경우(11-24 재현) ③ 따옴표로 감싼 and/or 단어 검색(rev 2에서 생긴 위험) ④ 허가된 보안 스캐너 |
| 1000002 | xss | **낮음 (안내 위주)** | 실습 앱 `/search`는 항상 200을 돌려줘서 XSS는 거의 항상 SEV1이 됨. 반사형 XSS에서 200은 「스크립트가 실행됐다」는 증거가 아님(`rule_catalog.json` XSS `notes`). **시연의 격리 대상으로 쓰지 않음** | ① HTML 코드 조각을 그대로 검색 ② `<script` 문자열이 든 보안 교육 자료 검색 |
| 1000003 | bruteforce | **권장** | 같은 출발지가 계속 연결을 시도하는 공격이라 끊으면 바로 멈춤 | ① 관리자가 1분 안에 SSH 창 여러 개 ② scp/rsync 연속 실행 ③ Ansible 등 자동화 도구 |
| 1000004 | portscan | **안내만** | SEV3, 정찰 단계라 아직 피해가 없음 | ① 서비스 포트를 추가했는데 제외 목록(22,80)을 갱신하지 않음 ② 모니터링 도구의 다중 포트 헬스 체크 |
| 1000005 | c2_beacon | **권장** | 주기적인 제어 연결은 끊는 것이 기본 대응. 실습망에서는 attacker→victim-web:8443 방향으로 단순화했음(카탈로그 `notes`) | ① 8443 정상 헬스 체크·모니터링 에이전트 ② 30초 안 여러 번 새로 고침하는 정상 사용자 |
| 1000006 | ssrf | 200(SEV1)이면 **권장**, 403(SEV3)이면 **안내만** | 200은 서버가 내부 주소를 실제로 조회했다는 뜻. 403은 내부 대상이 거절한 경우 | ① URL 미리보기 같은 정상 기능에 내부 링크 ② 관리자의 내부 상태 확인 요청 |

**권장이 「자동 격리」를 뜻하지 않습니다.** 모든 경우에 사람이 확인 페이지에서 요청 내용을 보고 승인합니다. 이 표는 그 판단을 돕는 기준입니다.

## 3. 격리 링크가 만들어지는 조건 (구현됨 — 코드로 확인)

경보 응답의 `isolation_token`(`backend/main.py:324`)은 아래 조건을 **모두** 만족할 때만 발급되고, 토큰이 있는 SEV1 경보에만 Discord 알림에 「격리 확인」 링크가 붙습니다(`frontend/index.html:3535-3537`).

| 조건 | 실제 값 | 근거 |
|---|---|---|
| 기능 스위치 | 서버를 `ISOLATION_ENABLED=1`로 켰을 때만. 아니면 토큰은 항상 `null`, docker도 호출 안 함 | `backend/isolation.py:47`, `README.md` 「선택 기능: 승인 기반 격리」 |
| 출발지 IP | `172.28.0.100` 하나 (`attacker` 컨테이너) | `backend/isolation.py:13` |
| 심각도 | **SEV1만**. SEV2(SSH 1000003·C2 1000005)는 링크가 만들어지지 않음 | `backend/isolation.py:14`, `:71-81` |
| 경보 나이 | 경보 시각이 지금부터 **5분(300초) 이내**. 그래서 pcap 업로드로 들어온 과거 경보(예: 실제 녹화)는 자동으로 제외됨 | `backend/isolation.py:16`, `:71-81` |
| 토큰 | 경보당 1개, **1회용**, 발급 후 **10분(600초)** 유효 | `backend/isolation.py:15`, `:83-100` |
| 실행 | 확인 페이지는 조회만 함. 「승인(격리 실행)」 버튼을 눌러야 `POST /api/isolate` 호출 | `frontend/isolate.html:26`, `README.md` |
| 최종 판단 | 링크를 받은 **사람** | PM 결정(2026-11-26) |

**종류(SID)로는 거르지 않습니다.** 위 조건만 맞으면 XSS(1000002)에도 링크가 붙습니다. 2절에서 XSS를 「낮음」으로 둔 이유가 여기에 있습니다.

### ⚠ 링크가 왔다고 다 격리 대상은 아닙니다 (실측 근거)

위 조건대로 `.100`에서 온 SEV1은 **종류와 상관없이** 링크가 갑니다. 시연 스크립트(`lab-traffic.sh`)를 녹화한 `c2_ssrf.pcap`을 Suricata와 팀 백엔드 파서로 돌려 보면(2026-11-26 확인) SEV1이 3건 나옵니다.

| 시각(녹화본 기준) | SID | 종류 | 요청 | 응답 | SEV | 링크 | 2절 기준 |
|---|---|---|---|---|---|---|---|
| 20:32:38 | 1000001 | sqli | `/login?username=admin'%20OR%20'1'='1'--&password=[MASKED]` | 200 | SEV1 | 옴 | **권장 — 시연에서 누를 링크** |
| 20:32:38 | 1000002 | xss | `/search?q=%3Cscript%3Ealert(1)%3C/script%3E` | 200 | SEV1 | 옴 | 낮음 — **누르지 않음** |
| 20:33:14 | 1000006 | ssrf | `/fetch?url=http%3A%2F%2F172.28.0.10%2Fhealth` | 200 | SEV1 | 옴 | 권장 (시연에서는 SQLi 하나만 사용) |

여기에 시연 장면 3의 정상 검색어 오탐(SQLi SEV1)이 더해지면 링크는 4개가 됩니다. 시연에서 누를 링크는 **SQLi 진짜 공격 하나**로 정합니다(`docs/isolation_demo_script.md`와 같음).

> **주의: Discord 메시지와 확인 페이지에는 요청 주소(`raw_url`)가 나오지 않습니다.**
> - Discord 알림 항목: 제목(심각도), 설명(시그니처), 카테고리/SID, MITRE, 출발지 → 목적지, 판정 상태, 격리 확인 링크 — 경보 번호도 나오지 않음 (`frontend/index.html:3555` `buildAlertEmbed`)
> - 확인 페이지 항목: 번호, 시간, 심각도, HTTP 상태, 시그니처, 출발지 → 목적지 (`frontend/isolate.html:108-117`)
>
> 그래서 SQLi 진짜 공격과 장면 3의 SQLi 오탐은 링크만 보면 **똑같이 보입니다**(둘 다 `SQLI (1000001)`, `172.28.0.100 → 172.28.0.10:80`, SEV1, HTTP 200). 승인 전에 확인 페이지의 **번호**를 대시보드 경보 상세에서 찾아 요청 주소에 `admin'`·`OR`이 있는지 확인합니다.

> 실제 녹화(`real_1125_1736.pcap`)의 `.100` 경보 30건도 같은 모양입니다. SEV1은 5건인데 그중 4건이 XSS, 1건이 SQLi였습니다(`frontend/mock_demo_data.js`의 `DEMO_REAL_ALERTS`로 직접 센 값). 즉 「SEV1 링크」의 상당수가 격리 권장이 낮은 XSS일 수 있습니다.
