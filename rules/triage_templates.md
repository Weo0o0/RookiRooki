# 트리아지 오탐(FP) 근거와 메모 템플릿 (룰 담당)

| 항목 | 내용 |
|---|---|
| 기준 코드 | 최신 main `a9f69b3` (2026-11-26, 격리·트리아지 PR #34·#35·#39 머지 후) |
| 작성 | 배기윤 (룰 담당) |
| 쓰는 곳 | 웹 경보 상세의 트리아지 칸 — 「관찰된 사실(observation)」, 「분석가 추정(assessment)」 |
| 바꾼 파일 | **없음.** 새로 추가한 판단 문서입니다. |

> **트리아지란?** 경보 하나하나를 사람이 보고 「진짜 공격(TP)인지, 오탐(FP)인지, 아직 모르는지(보류)」를 정하고 근거를 남기는 일입니다.

## 0. 저장 규칙 (사실, `backend/main.py:92-100`)

| 칸 | 허용 값 | 비고 |
|---|---|---|
| 판정 `verdict` | `TP` / `FP` / `UNREVIEWED` | `UNREVIEWED`는 화면에서 「보류(미확정)」로 표시됨 (`frontend/index.html:1588`). **FP로 저장하면 기본 목록·통계에서 빠지고**, 「오탐(FP) 포함해서 보기」를 켜면 다시 보임 (`backend/main.py:442-451`) |
| 신뢰도 `confidence` | `HIGH` / `MEDIUM` / `LOW` | |
| 관찰된 사실 `observation` | 글, 최대 2000자 | 서버가 비밀번호류 값을 `[MASKED]`로 가림 |
| 분석가 추정 `assessment` | 글, 최대 2000자 | 같음 |
| 담당자 `analyst` | 글, 최대 50자 | 구현됨 (`backend/main.py:23`, `:99`) |
| 조치 상태 `action_status` | 격리함 `ISOLATED` / 안내만 `GUIDE_ONLY` / 없음 `NONE` | 구현됨 (`backend/main.py:100`). 화면 표시는 「격리함·안내만·없음」 |

표에 없는 키를 보내면 서버가 422로 거절합니다(`extra: forbid`).

**관찰된 사실 vs 분석가 추정 — 섞지 않습니다.**
- 관찰된 사실: 화면·로그에서 **누가 봐도 같은** 값(출발지, 목적지, 요청 주소, 응답 코드, SID, SEV).
- 분석가 추정: 그 사실을 보고 **내가 내린 해석**(공격 같다/아니다, 왜).

### 1-2. 왜 오탐(FP)인가 — 근거 5가지

| # | 근거 | 확인 방법 |
|---|---|---|
| 1 | **SQL 문법이 없습니다.** 룰에 걸린 부분은 `union select` 두 단어뿐이고, 따옴표(`'` `"`), `--`, `#`, `/*` 같은 SQL 문자열·주석 문법이 없습니다. | 요청 주소를 그대로 읽기 |
| 2 | **문장으로 읽힙니다.** `european union select committee`는 일반 영어 문장(유럽연합 선별 위원회)입니다. | 요청 주소의 `q=` 값 |
| 3 | **200이 공격 성공 증거가 아닙니다.** 실습 앱 `/search`는 검색어와 상관없이 항상 200을 돌려줍니다. 그래서 이 경보의 SEV1 격상은 의미가 없습니다. | `rule_catalog.json` XSS `notes` |
| 4 | **반복·동반 패턴이 없습니다.** 이 출발지의 경보는 이 2건뿐이고, 포트 스캔·SSH 같은 다른 룰 경보가 같이 오지 않았습니다. 진짜 공격자는 보통 정찰 → 침투처럼 여러 경보를 남깁니다. | 1-1 표 마지막 줄 |
| 5 | **이미 알려진 오탐입니다.** `rule_catalog.json` sqli의 `false_positives`에 「검색어에 `union select` 단어가 그대로 포함된 경우 - 2026-11-24 재현 확인」으로 적혀 있습니다. | `rule_catalog.json` |

**판정 (제안):** FP · 신뢰도 HIGH · 조치 상태 「없음」

### 1-3. 진짜 공격과 비교

| 항목 | 오탐 (`.50`) | 진짜 공격 (`lab-traffic.sh` 2단계) |
|---|---|---|
| 화면에 보이는 요청 | `/search?q=european+union+select+committee` | `/login?username=admin'%20OR%20'1'='1'--&password=[MASKED]` |
| 풀어서 읽으면 | european union select committee | `admin' OR '1'='1'--` (`%20`은 공백) |
| 따옴표·`--` | 없음 | 있음 |
| 의미 | 일반 문장 | 「항상 참」 조건으로 로그인 검사를 우회하는 문법 |
| HTTP 200의 뜻 | 검색 페이지는 항상 200 | 로그인이 통과했을 가능성 |
| 같은 출발지의 다른 경보 | 없음 | XSS·SSH·스캔·C2·SSRF가 이어짐 |
| 판정 | **FP** | **TP** |

진짜 공격 쪽 요청은 `c2_ssrf.pcap`(같은 스크립트 녹화본)을 팀 백엔드 파서로 돌려 확인한 값입니다(2026-11-26). 비밀번호 칸은 백엔드가 `[MASKED]`로 가렸습니다.

> 같은 검색어를 attacker(`.100`)가 보내도 SID 1000001 경보가 납니다 — 실습망 IP로 만든 pcap을 Suricata + `rules/custom.rules`로 돌려 확인(2026-11-26, 오프라인). 실시간 캡처에서의 확인은 시나리오 리허설 1회차 항목입니다.

## 2. 메모 템플릿 7종

**쓰는 규칙**
- `[ ]`는 실제 경보 값으로 바꿉니다. **모르는 값은 지어내지 말고 비워 둡니다.**
- 비밀번호·토큰 값은 적지 않습니다(서버가 가리지만 처음부터 안 쓰는 것이 안전).
- SSH·포트 스캔·C2는 **횟수로 판단하는 룰**(`threshold: type both`)이라, 경보 1건은 「룰 기준 횟수를 넘겼다」는 뜻입니다. **정확한 시도 횟수는 경보에 들어 있지 않습니다.** 그래서 템플릿에 횟수 대신 「룰 기준 이상」이라고 적습니다.
  - 작업 지시서(`02_룰_작업.md` 2-2)의 템플릿에는 `[N]회` 칸이 있었습니다. 「실제 경보에서 확인한 값만 넣는다」는 지시서 규칙을 지키면 이 칸은 항상 비게 되므로, 위처럼 바꿨습니다. 횟수를 꼭 적어야 한다면 경보가 아닌 다른 기록(예: 같은 출발지의 연결 로그)에서 센 값을 적고 출처를 함께 씁니다. **(PM 확인 필요)**

| # | 상황 | 판정 | 조치 상태 | 관찰된 사실 | 분석가 추정 |
|---|---|---|---|---|---|
| 1 | 검색어 오탐 | FP | 없음 | `[출발지] → [목적지]:80, GET [요청 주소], HTTP 200, SID 1000001, SEV1. 요청에 따옴표·--·# 없음. 같은 출발지의 다른 경보 [있음/없음].` | `일반 검색어에 union select 단어가 들어간 오탐으로 보임. /search는 항상 200이라 SEV1 격상은 공격 성공 근거가 아님. 카탈로그의 알려진 오탐과 같음. 조치 없음.` |
| 2 | SQLi 진짜 공격 | TP | 격리함(승인했다면) / 안내만 | `[출발지] → [목적지]:80, GET [요청 주소 — 따옴표·OR·-- 포함], HTTP [응답 코드], SID 1000001, SEV[ ].` | `로그인 우회를 노린 SQL 인젝션. [200이면: 우회에 성공했을 가능성이 있음 / 403·500이면: 시도만 확인됨]. [격리 승인함 / 격리 대신 차단 명령 안내].` |
| 3 | SSH 무차별 대입 | TP | 격리함 / 안내만 | `[출발지] → 172.28.0.11:22, 룰 기준(60초 안 새 연결 4회 이상)을 넘긴 반복 접속, SID 1000003, SEV2.` | `반복 로그인 시도로 보임. [관리자 작업·자동화 도구가 아님을 확인함 / 확인 못 함]. 로그인 성공 여부는 네트워크 경보만으로 알 수 없음.` |
| 4 | 포트 스캔 | TP | 안내만 | `[출발지] → [목적지], 룰 기준(10초 안 22·80 외 포트로 SYN 20회 이상)을 넘김, SID 1000004, SEV3.` | `정찰 단계로 보임. 아직 피해 없음. 격리 대신 모니터링.` |
| 5 | C2 비콘 | TP | 격리함 / 안내만 | `[출발지] → [목적지]:8443, 룰 기준(30초 안 새 연결 5회 이상)을 넘김, SID 1000005, SEV2.` | `주기적 접속으로 보임. [정상 헬스 체크가 아님을 확인함 / 확인 못 함].` |
| 6 | SSRF 200 | TP | 격리함 / 안내만 | `[출발지] → [목적지]:80, GET /fetch?url=[내부 주소], HTTP 200, SID 1000006, SEV1.` | `서버가 내부 주소를 대신 조회함. 내부 조회 성공.` |
| 7 | SSRF 403 | TP 또는 보류 | 안내만 | `[출발지] → [목적지]:80, GET /fetch?url=[내부 주소], HTTP 403, SID 1000006, SEV3.` | `내부 대상이 접속을 거절함. 시도만 확인됨.` |

> 포트 스캔 경보의 목적지 포트(예: `172.28.0.10:78`)는 임계치를 넘긴 **그 패킷**의 포트라 대표값이 아닙니다(`rule_catalog.json` portscan `notes`). 그래서 4번 템플릿에는 포트 번호를 쓰지 않습니다.

## 3. 판정 가이드 (제안)

위에서부터 차례로 묻습니다.

| 질문 | 예 → | 아니오 → |
|---|---|---|
| ① 요청이 문장·검색어처럼 읽히는가? | FP 쪽 (②도 확인) | ②로 |
| ② 따옴표·주석·`<script`처럼 공격 문법이 있는가? | TP 쪽 | FP 쪽 |
| ③ 같은 출발지에서 다른 경보가 이어지는가? | TP 쪽 | 보류 |
| ④ 카탈로그 `false_positives`에 같은 사례가 있는가? | FP 근거로 인용 | — |
| ⑤ 그래도 판단할 증거가 부족한가? | 보류(`UNREVIEWED`) 유지 | — |

**보류도 정답입니다.** 증거 없이 TP/FP를 정하는 것보다, 보류로 두고 무엇을 더 봐야 하는지 메모에 적는 편이 낫습니다.
