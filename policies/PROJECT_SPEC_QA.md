## 6. 사후 분석: 라이브 SEV1 격상 알림 누락 (2026-11-26)

비난하지 않는 관점으로 씁니다. 사람의 실수가 아니라 구조와 확인 과정에서 원인을 찾습니다.

### 6-1. 요약

라이브 모드에서 SQL 인젝션 경보가 SEV1이 되었는데도 웹 알림 이력과 Discord 자동 알림이 오지 않았습니다. 트리아지 화면의 수동 「알림 전송」은 정상이었습니다. PR #42로 수정했습니다.

### 6-3. 사실과 추정

| 구분 | 내용 |
|---|---|
| 사실 | 라이브에서 경보가 SEV3로 먼저 저장되고, 늦게 온 HTTP 200으로 **같은 id**가 SEV1로 UPDATE됨 (`backend/live_capture.py:84-104`) |
| 사실 | 수정 전 프론트 `notifyNewAlerts`는 **처음 보는 id**에만 알림을 보냄. SEV1로 바뀐 순간에는 이미 본 id라 아무것도 하지 않음 |
| 사실 | PCAP 업로드는 파일을 한 번에 처리해 처음부터 SEV1로 저장되므로 이 문제가 없음 (`backend/eve_parser.py:101`) |
| 사실 | 수정 후 `sev1NotifiedIds`로 SEV1 알림을 보낸 id를 따로 기억해, 새 SEV1과 격상 SEV1을 **1번만** 보냄 (`frontend/index.html:1366-1412`) |
| 추정 | Suricata가 `alert` 기록을 `http` 응답 기록보다 먼저 쓰는 순서 때문에 생김. 트래픽이 많거나 느리면 더 자주 생길 수 있음 |

### 6-4. 5 Whys

1. 왜 Discord 알림이 안 왔나? → 자동 알림이 「처음 볼 때 SEV1인 경보」에만 나갔기 때문.
2. 왜 처음 볼 때 SEV1이 아니었나? → 라이브에서는 응답 기록이 늦게 와서 SEV3로 먼저 저장됐기 때문.
3. 왜 새 경보가 아니라 같은 경보가 바뀌었나? → 중복 저장을 막으려고 백엔드가 같은 행을 UPDATE하도록 설계했기 때문(PR #25).
4. 왜 프론트가 바뀐 것을 몰랐나? → 알림 로직이 심각도가 저장 순간 확정되는 PCAP·Mock 흐름을 기준으로 만들어져 id만 비교했기 때문.
5. 왜 더 일찍 못 찾았나? → 라이브 + Discord + 실습망을 모두 켠 끝까지 시험을 11/26 밤에 처음 했기 때문.

**SLA 구현 제안 (코드에는 넣지 않음).** 지금은 SLA를 계산하거나 재알림하는 코드가 없습니다. 가장 작은 방법은 경보 응답에 「초기 대응 기한」을 붙이고 화면에 남은 시간을 보여 주는 것입니다.

```python
# backend/main.py (제안) — 맨 위 import에 timedelta 추가 필요
SLA_MINUTES = {"SEV1": 5, "SEV2": 15, "SEV3": 60}  # SEV4는 예약 등급

def sla_due_at(row):
    minutes = SLA_MINUTES.get(row["severity"])
    created = isolation.parse_alert_time(row["timestamp"])
    if minutes is None or created is None:
        return None
    return (created + timedelta(minutes=minutes)).isoformat()

# build_alert_dict 반환값에 추가
#   "sla_due_at": sla_due_at(row),
```

```javascript
// frontend/index.html (제안): 목록에 남은 시간 표시, 보류(미확정) 경보만
const left = Math.round((new Date(alert.sla_due_at) - Date.now()) / 60000);
badge.textContent = left >= 0 ? `대응 ${left}분 남음` : `대응 기한 ${-left}분 초과`;
```

재알림(SEV1 15분, SEV2 30분)은 트리아지 저장 전까지 같은 경보를 주기마다 다시 보내는 방식이며, 알림이 많아질 수 있어 위 표시를 먼저 넣은 뒤 정합니다.
